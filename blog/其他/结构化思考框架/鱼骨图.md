# 鱼骨图

[[toc]]

鱼骨图又称石川图或因果图，由日本质量管理专家石川馨提出，因形状像一条鱼的骨架而得名。它把一个问题（鱼头）和导致它的众多原因（鱼骨）画在同一张图上，用于在团队中系统性地罗列和归类原因。它解决的问题是：面对一个复杂问题，如何避免只想到自己熟悉的那几个原因，把可能性铺全。制造业的质量改进、服务业的流程优化、软件团队的故障复盘都在用它。

## 一句话概括

> 鱼头是问题，主干是原因的类别，小刺是具体原因，把可能性一次铺满再逐一排查。

## 核心思想

鱼骨图的价值在于**把“想原因”从个人行为变成团队行为**。一个人想原因，能想到的往往是自己职责范围内的那几项；把不同岗位的人聚到一张图前，工程师会想到技术，操作工会想到设备，质检会想到测量方法。图本身不产生洞见，它产生的是一张覆盖面足够广的候选清单。

它和纯粹的原因清单的区别在于**分类结构**。鱼骨图要求先把原因归到几个主干类别下，再往每条主干上挂具体原因。这个结构有两个好处：一是提示你检查每个类别是否都想到了，二是当同类原因被写在同一条骨头上时，重复和交叉会立刻显现。

最经典的主干分类是 **6M**，即人（Man）、机（Machine）、料（Material）、法（Method）、测（Measurement）、环（Environment）。这套分类源自制造业，但可以按场景替换。服务业常用人、流程、系统、环境、客户；软件团队常用代码、配置、依赖、数据、基础设施、人为操作。**类别不是重点，覆盖全面才是重点**，选定一套后要能解释为什么这组类别覆盖了全部可能。

使用鱼骨图有一条纪律：**先发散，后收敛**。画图阶段禁止评价，任何听起来离谱的原因都要写上去，因为过早否定会扼杀团队里最了解现场的那个人提供的关键线索。等图铺满之后，才进入投票和验证阶段，用数据筛掉不成立的原因。

还有一个常被忽略的细节：**鱼骨图只负责提出假设，不负责证明**。图上的每条原因都是一个待验证的猜想，画得再漂亮也不能直接当结论。真正的结论来自后续的排查，通常是把鱼骨图和 5Why 组合使用——鱼骨图给出候选，5Why 把最可疑的候选追到底。

### 主干类别怎么选

6M 只是众多可选分类中的一种。选哪一套，取决于你的场景里“哪些方面是可以动手改变的”。

| 场景 | 常用主干类别 |
| --- | --- |
| 制造业质量 | 人、机、料、法、测、环（6M） |
| 服务业流程 | 人员、流程、系统、环境、客户 |
| 软件故障 | 代码、配置、依赖、数据、基础设施、人为操作 |
| 医疗安全 | 患者因素、人员、流程、设备、环境、沟通 |
| 项目管理 | 需求、资源、进度、沟通、外部依赖、技术 |
| 销售业绩 | 产品、价格、渠道、人员、客户、竞品 |

选定之后要做一个动作：**逐条主干问一遍“这一类里有没有我们还没想到的”**。这一步比填充内容更重要，因为遗漏通常不是发生在某条骨头内部，而是整条主干根本没人想到。

### 为什么必须用团队而不是一个人

鱼骨图的设计初衷是让不同岗位的人在同一张图上贡献各自视角。一个人画图，主干类别会不自觉地围绕自己熟悉的领域展开：技术背景的人容易只画“代码”“配置”两条主干，而忽略“人为操作”和“基础设施”。把运营、客服、一线操作工都拉进来，图上的主干才会真正覆盖完整。

## 怎么用

1. **写出鱼头**。在图的右侧写清问题，包括现象、时间、范围。问题越具体，后面越容易聚焦，例如“三号线焊接工序不良率从 2% 上升到 5%”。
2. **确定主干类别**。选定一组分类，制造业可用 6M，其他场景自行定义，通常 4 到 6 条主干比较合适。
3. **发散填充**。团队每个人把自己想到的原因写便利贴贴到对应骨头上，过程中不讨论、不否定。
4. **归类去重**。把意思相同的原因合并，把放错类别的移到正确的主干下。
5. **检查覆盖**。逐条主干问“这个类别下还有没有我们没提到的”，特别检查那些平时没人负责的类别。
6. **投票筛选**。团队对最可能的原因投票，或者用现有数据先做一轮粗筛，选出前三个重点。
7. **逐条验证**。对重点原因用数据、实验或现场观察验证，这一步常配合 5Why 继续追问。
8. **制定对策并回填**。确认原因后制定对策，把对策写在对应骨头旁边，形成“问题—原因—对策”的完整记录。

## 示例

某餐饮连锁门店的顾客投诉集中在“上菜太慢”，用鱼骨图分析。

| 主干类别 | 具体原因 |
| --- | --- |
| 人（人员） | 高峰期服务员不足；新员工不熟悉菜单；后厨分工不明确 |
| 机（设备） | 两台灶具中的一台故障停用；出餐口打印机偶尔卡纸 |
| 料（物料） | 部分食材需临时解冻；热门菜品备料不足需现切 |
| 法（方法） | 点单到后厨靠口头传递，易遗漏；没有明确的出餐顺序规则 |
| 测（测量） | 没有统计各环节耗时，无法定位瓶颈 |
| 环（环境） | 后厨通道狭窄，传菜与备料动线交叉 |

铺完之后团队投票，发现“点单靠口头传递”和“灶具故障”得票最高。进一步查数据，发现故障灶具停用的那几天正是投诉最集中的时段，同时口头传递导致的漏单占投诉量的三分之一。两个原因都得到了验证，对策分别是立即维修灶具和上线电子点单系统。

再看一个软件场景，某接口错误率突然升高：

| 主干类别 | 具体原因 |
| --- | --- |
| 代码 | 最近一次发版引入了新的重试逻辑 |
| 配置 | 生产环境的超时阈值与测试环境不一致 |
| 依赖 | 上游服务当天做过扩容，连接池参数未同步 |
| 数据 | 出现了一批字段缺失的历史数据 |
| 基础设施 | 某台实例磁盘使用率接近上限 |
| 人为操作 | 运维在当天调整过负载均衡权重 |

这张图的用处不在于直接给出答案，而在于它把“错误率升高”这个笼统的问题拆成了六个可以分别查证的方向，团队可以并行排查而不是所有人挤在一个方向上。

## 适用场景

- 质量改进：不良率、返工率、客诉率的系统性原因分析。
- 生产现场：设备故障、产能不足、安全事故的原因排查。
- 服务流程：等待时间长、满意度下降、投诉集中的归因。
- 软件故障复盘：线上事故的多方向排查与事后总结。
- 医疗与安全：不良事件、差错事件的团队分析会议。
- 项目管理：进度延误、预算超支的原因归类。
- 团队工作坊：作为头脑风暴的载体，让不同岗位的声音都被记录。

## 常见误区

- **鱼头太模糊**。写成“质量不好”这类问题，图会失去焦点，什么原因都挂得上去。
- **画完不验证**。把图当成结论直接开始改，改的可能是猜出来的原因。
- **过早否定**。画图阶段就争论“这个不可能”，会把最了解现场的人的声音压下去。
- **主干类别缺项**。只画了人和方法两条主干，测量、环境类的原因全被漏掉。
- **同一原因挂多处**。没做去重，同一条原因在三条骨头上各写一遍，导致投票时被高估。
- **只有图没有行动**。分析会开完，图贴在墙上，没有一条原因被真正验证。
- **与 5Why 混用不当**。鱼骨图上某条原因只写到“操作不规范”就停下，没有继续追问为什么会不规范。
- **类别自定义后不检查覆盖**。随意定义主干，没有回头确认是否穷尽，遗漏照样发生。

## 相关工具

- **5Why 分析法**：鱼骨图横向铺开候选原因，5Why 对选中原因纵向追到底，是最经典的组合。
- **MECE 原则**：用于检查主干类别和骨头上原因是否不重不漏，避免同类原因被重复计算。
- **逻辑树**：鱼骨图是发散式的多维度罗列，逻辑树是收敛式的逐层分解，两者互补。
- **5W2H 分析法**：可以借用 5W2H 的维度作为主干类别，也可以用它来精确描述鱼头。
- **金字塔原理**：把鱼骨图的验证结果整理成结论先行的复盘报告。
- **假设驱动与议题树**：鱼骨图上的每条原因本质都是一个假设，需要按影响和成本排序后逐一验证。
