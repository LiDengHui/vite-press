# 金字塔原理

[[toc]]

金字塔原理由芭芭拉·明托提出，最初是为了解决咨询顾问写报告时“信息很多但说不清楚”的问题。它主张思想应当组织成一个金字塔：结论在最顶端，下面是支撑结论的理由，再下面是支撑理由的事实和数据。它同时管两件事——怎么想清楚，以及怎么说明白。写方案、做汇报、写邮件、准备面试回答的人，都在用它。

## 一句话概括

> 结论先行，以上统下，归类分组，逻辑递进。

## 核心思想

金字塔原理的第一条是**结论先行**。读者最想知道的是“所以呢”，而不是你的推导过程。先把结论放出来，读者才有框架去接收后面的细节。这和学术写作的习惯相反——学术论文先把方法、数据铺开，最后才给结论；而工作场景里读者时间有限、注意力分散，先给结论是对读者的尊重。

第二条是**以上统下**。金字塔里任何一个层次上的思想，都必须是它下面那一组思想的概括。上一层的结论要能被下一层完整支撑，下一层的每条论据都应当回答“为什么上一层的结论成立”。这条规则是双向的：向下检查有没有支撑，向上检查有没有概括。

第三条是**归类分组**。同一组里的思想必须属于同一逻辑范畴，并且这一组要满足 MECE，即相互独立、完全穷尽。分组是人的认知习惯，人一次只能处理有限的信息块，把信息预先分好组，等于替读者降低了理解成本。

第四条是**逻辑递进**。同一组里的思想要按某种明确的顺序排列，常见的有时间顺序、结构顺序、重要性顺序。顺序不是装饰，它决定了读者先看到什么、后看到什么，从而影响他理解论证的方式。

除了这四条纵向和横向的规则，明托还给出了序言的组织方式——**SCQA 结构**：情境（Situation）、冲突（Complication）、疑问（Question）、回答（Answer）。先描述一个读者认同的背景，再指出背景中出现的冲突，冲突自然引出疑问，而你的结论就是对疑问的回答。这个顺序把“我为什么要听你说”这件事解决了，常见于报告开头、演讲开场、方案摘要。

明托还特别指出，同一组思想只有两种组织方式：**归纳推理**和**演绎推理**。演绎是线性的，链条长、容易在某一步被质疑，读者必须跟着走完才认账；归纳是把一组同类事实概括成一句结论，读者可以逐条检验。因此明托建议在表达时优先使用归纳，把演绎留给真正需要推导的场合。这一点常被忽略，却是金字塔原理里最实用的一条。

### 纵向关系与横向关系

金字塔的规则可以拆成两个方向来看，检查时分开做，效率更高。

| 方向 | 规则 | 检查问题 |
| --- | --- | --- |
| 纵向 | 以上统下 | 上一层的结论，是否被下一层的每一条完整支撑？下一层的每一条，是否都在回答上一层的“为什么”或“怎么做”？ |
| 横向 | 归类分组 | 同一组的理由是否属于同一逻辑范畴？它们之间是否互相包含？ |
| 横向 | 逻辑递进 | 同一组的理由是否按同一种顺序排列？顺序是否讲得出来？ |

纵向断链最常见的表现是“答非所问”：上一层说“成本可控”，下一层摆出的却是一份组织架构图。横向出问题最常见的表现是“分不清类”：一组理由里既有原因又有对策，读者不知道你在论证还是在提议。

### 序言为什么不能省

结论先行不等于开门见山。直接抛结论的风险是读者缺少判断这个结论重要性的背景，他会觉得“这跟我有什么关系”。SCQA 的作用就是先把读者放到一个认同的位置上：情境是双方都承认的事实，冲突是这个事实带来的麻烦，疑问是从麻烦里自然长出来的问题，回答就是你的结论。四句话的顺序不能颠倒，颠倒之后疑问就失去了来源，结论也就失去了必要性。

## 怎么用

1. **先写序言**。用 SCQA 四句话搭出背景：现状是什么（S）、出了什么问题（C）、因此要回答什么问题（Q）、你的答案是什么（A）。这一步决定了整篇文档的基调。
2. **定塔尖**。把 A 写成一句完整的、有判断的句子。避免“关于某问题的探讨”这类没有观点的标题式结论。
3. **找支撑理由**。问“为什么这个结论成立”，列出 3 到 5 条理由。理由之间必须满足 MECE，不能互相包含。
4. **检查纵向关系**。对每条理由继续追问“凭什么这么说”，把事实和数据挂到它下面。如果一个理由下面挂不出证据，说明它只是感觉，不是论据。
5. **排横向顺序**。决定同一组理由是时间顺序、结构顺序还是重要性顺序，并检查每组是否用同一种顺序。
6. **判断推理类型**。看这一组是归纳还是演绎。如果是演绎，考虑能否改写成归纳，让读者更容易接受。
7. **自上而下通读**。只看每一层的标题句，看能否连成一段通顺的话。连不起来，说明结构有问题。
8. **自下而上复核**。只看最底层的证据，问它们能否支撑到塔尖。有证据支撑不到的地方，就是论证的薄弱点。

## 示例

假设要向管理层汇报“是否应当把客服团队迁到二线城市”。

先写 SCQA：

| 要素 | 内容 |
| --- | --- |
| 情境 S | 公司客服团队现有 120 人，全部位于一线城市，过去三年人力成本年均上涨约 12% |
| 冲突 C | 若维持现状，明年客服人力预算将超出核定额度，而业务量仍在增长 |
| 疑问 Q | 在保证服务质量的前提下，如何降低客服人力成本 |
| 回答 A | 建议将其中 80 个标准化岗位迁至二线城市，保留 40 个复杂客诉岗在一线城市 |

然后搭金字塔：

| 层级 | 内容 |
| --- | --- |
| 塔尖 | 分拆迁移，而不是整体迁移 |
| 理由一（成本） | 二线城市同岗位薪酬约为一线城市的 65%，迁移 80 人每年可节省可观成本 |
| 理由二（风险可控） | 标准化岗位的答复脚本化程度高，异地服务质量差异可以控制在可接受范围 |
| 理由三（保留能力） | 复杂客诉需要跨部门协作和现场支持，留在一线城市更合适 |
| 支撑证据 | 薪酬调研数据、试点团队的服务指标对比、复杂客诉的分类占比 |

这里三条理由是结构顺序：成本、风险、能力，分别回答“划不划算”“行不行得通”“该不该全迁”，互不重叠，合起来覆盖了决策需要考虑的主要方面。

同一组理由也可以改写成归纳式表达：“迁移的可行性取决于成本、服务质量与组织能力三个条件，试点结果表明三者都满足，因此建议迁移。”这样的句子让读者可以先判断每个条件是否成立，而不必跟着一条长长的推理链。

### 常用结构模板

不同场景可以套用不同的骨架，塔尖的写法决定了整篇文档的调性。

| 场景 | 塔尖写法 | 支撑理由的顺序 |
| --- | --- | --- |
| 建议类（要不要做） | 建议做某事，以及做到什么程度 | 收益、可行性、风险可控性 |
| 归因类（为什么发生） | 某结果由某几个原因导致 | 原因按影响程度从大到小 |
| 汇报类（做了什么） | 阶段目标达成情况与下一步 | 结果、关键动作、问题与请求 |
| 方案对比类（选哪个） | 推荐某方案 | 评估标准逐条对比 |
| 请求类（要资源） | 申请某项资源支持 | 必要性、投入产出、不做的后果 |

模板的价值在于它逼你先把塔尖写出来。很多人写不出塔尖，是因为他自己还没想清楚到底要什么——这时候问题不在写作，在思考。

## 适用场景

- 书面汇报：周报、月报、项目总结、立项报告的结构搭建。
- 口头表达：向上汇报、面试回答、会议发言的提纲设计。
- 方案撰写：先把结论和理由定下来，再补细节，避免边写边想。
- 邮件与消息：重要邮件用结论开头的写法，能让对方在十秒内抓住重点。
- PPT 结构：每一页的标题就是该页的结论，多页连起来是一个完整论证。
- 问题分析：先给出对问题的判断，再用证据支撑，而不是罗列所有信息。

## 常见误区

- **只有结论没有理由**。结论先行不等于只给结论，没有支撑的判断是断言，不是论证。
- **把主题当结论**。“关于客服成本的思考”是主题，“建议迁移 80 个岗位”才是结论。
- **同组理由互相包含**。比如“成本高”和“人力贵”其实是同一条，放在一组里就破坏了 MECE。
- **纵向断链**。中间某一层的结论下面挂着的事实，其实支撑的是另一层，导致结构错位。
- **横向顺序混乱**。一组里既有时间顺序又有重要性顺序，读者会失去方向感。
- **滥用演绎**。把简单结论写成多段推理，读者还没走完就已经不信了。
- **序言缺失**。直接从结论开始，读者不知道背景和冲突，会觉得结论来得突然。
- **为了金字塔而金字塔**。把本来并列的清单硬套成论证结构，反而扭曲了原意。

## 相关工具

- **MECE 原则**：金字塔原理中“归类分组”的质量标准，保证同一层理由不重不漏。
- **逻辑树**：金字塔的自下而上构建版本，先把问题拆成树，再向上概括出结论。
- **SCQA 结构**：金字塔原理的序言写法，专门解决开头怎么让读者进入状态的问题。
- **归纳与演绎**：金字塔中同一组思想的两种组织方式，明托建议表达时优先用归纳。
- **假设驱动与议题树**：咨询项目里先给假设再验证，本质是把金字塔塔尖提前说出来，再用议题树去证实或证伪。
- **5W2H**：当理由不够具体时，用七个提问把一条笼统的理由展开成可验证的细节。
