# OKR目标与关键结果

[[toc]]

OKR 是 Objectives and Key Results 的缩写，中文一般译作"目标与关键结果"。它把"我们要去哪里"和"怎么知道已经到了"拆成两部分：Objective 是定性的、有方向感的目标，Key Results 是定量的、可验证的结果。

它源自英特尔，在安迪·格鲁夫手上成型，后来由约翰·杜尔引入谷歌并推广到大量科技公司。它解决的是团队各自忙碌、却说不清是否在推进最重要事情的问题。

## 一句话概括

> 用一句鼓舞人心的目标指明方向，用三到五个可量化的关键结果证明你确实走到了那里。

## 核心思想

OKR 的第一层逻辑是区分"目标"和"结果"。目标回答"为什么做、要做成什么样"，结果回答"做到什么程度算成功"。很多团队把任务清单当成目标，比如"完成用户调研""上线新功能"，这些是动作，不是结果。真正的结果应该像"新用户 7 日留存从 35% 提升到 45%"这样，能被验证、也能被质疑。

第二层逻辑是聚焦。人的注意力有限，一个季度能真正推动的重点通常只有两到三个。OKR 强制限定数量：每个周期 2 到 4 个目标，每个目标 3 到 5 个关键结果。数量限制本身就是一种取舍，逼着团队承认"不是所有事都同等重要"。

第三层逻辑是透明与对齐。OKR 通常全员公开，下级能看到上级的目标，平级能看到彼此的进度。这样既能避免重复劳动，也能让每个人理解自己手上的事情在整个组织里处于什么位置。对齐不是自上而下派发，而是上下沟通后的承诺。

第四层逻辑是把 OKR 和考核分开。谷歌的经验是 OKR 不直接决定薪酬。因为一旦目标挂钩奖金，人就会把目标定得保守，把风险藏起来，OKR 也就失去了牵引作用。OKR 鼓励挑战，完成 60% 到 70% 的挑战性目标通常被视为正常，而不是失败。

第五层逻辑是节奏。OKR 不是写完就贴在墙上的文件，它需要配套的检查节奏。周会看进展和风险，月度做中期调整，季度末评分复盘。没有节奏，OKR 会迅速变成一份无人问津的文档。

关于评分，常见做法是对每个关键结果打 0 到 1 分。评分的目的不是排名，而是学习：哪些假设成立，哪些判断失误。如果所有 KR 都轻松拿到 1 分，往往说明目标定得过于保守；如果全部接近 0 分，可能是目标脱离实际，也可能是执行出了问题。

需要分清 OKR 与 KPI 的分工：OKR 负责"进攻"，指向需要突破的方向；KPI 负责"防守"，监控业务健康度。两者并不互斥，但不要混在同一张表里互相打架。把监控型指标塞进 OKR，会让 OKR 变成一张冗长的报表，失去聚焦的作用。

OKR 也有不适合的场景。高度确定、重复性强的流水线工作，用 KPI 反而更清晰；需要长期投入、短期看不到结果的基础研究，硬套季度 OKR 可能逼出短视行为。工具的选择要匹配工作性质。

OKR 与 MBO 的关系也值得说明。OKR 继承了德鲁克目标管理的核心思想，但在两点上做了改进：一是强调公开透明，二是刻意与考核脱钩。理解这一点，就不会把 OKR 用成一张换了名字的绩效考核表。

最后一点是，OKR 的效果高度依赖信任文化。如果组织习惯用目标追责，公开 OKR 就会变成互相提防，大家只写有把握完成的事。OKR 要发挥作用，前提是允许失败、鼓励挑战。这也是它常常在推行一段时间后走样的原因。

## 怎么用

1. 确定周期。多数团队按季度设定 OKR，年度 OKR 作为方向，季度 OKR 作为执行单位。
2. 写 Objective。用一句话说明这个季度最重要的方向。
   - 要具体、有画面感，避免"提升效率"这类放之四海皆准的说法。
   - 目标可以是定性的，但必须让人一听就知道重心在哪。
3. 写 Key Results。每个目标配 3 到 5 条。
   - 必须是可衡量的结果而不是任务，用"从 X 到 Y"的形式写。
   - 写清基线和目标值，避免只有目标值没有起点。
4. 做对齐。向上看是否支撑了公司级目标，横向看是否与其他团队冲突或重复。
5. 全员公开。把 OKR 放在所有人都能看到的地方，让协作方知道你在这个季度看重什么。
6. 保持节奏。每周用短会检查进度、识别风险，只讨论"哪里卡住了"，不逐条汇报。
7. 季度末评分复盘。对每个 KR 打分，分析差距原因，决定哪些做法延续、哪些放弃。
8. 开始下一轮。把上一轮的结论和未解决的问题，作为下一轮目标设定的输入。

## 示例

一家 SaaS 公司某季度的 OKR 示例：

| 类型 | 内容 |
| --- | --- |
| Objective | 让新用户在第一周就感受到产品价值 |
| KR1 | 新用户 7 日留存率从 35% 提升到 45% |
| KR2 | 首次关键操作（创建第一个项目）的平均耗时从 12 分钟降到 5 分钟 |
| KR3 | 新手引导完成率从 48% 提升到 70% |
| KR4 | 首周内提交工单的比例从 22% 降到 15% |

对应的 KPI（用于监控健康度，不放进 OKR）：月度经常性收入、系统可用性、平均响应时长。OKR 管"这个季度要突破什么"，KPI 管"底线有没有守住"。

再看一个个人 OKR 的例子。某工程师的季度目标：

| 类型 | 内容 |
| --- | --- |
| Objective | 成为团队内 API 设计的可靠负责人 |
| KR1 | 主导完成 2 个核心接口的设计文档并通过评审 |
| KR2 | 把接口相关的线上缺陷从每季度 5 个降到 1 个以内 |
| KR3 | 在团队内做 1 次接口设计规范分享 |

个人 OKR 同样要公开、要能对齐团队方向。如果团队本季度的重点是"稳定性"，那么个人目标围绕接口质量，方向就是一致的。

## 适用场景

- 需要跨团队聚焦少数关键突破点的季度或半年度规划。
- 快速变化的业务环境，方向需要定期重估，不适合用年度固定指标。
- 知识型、创新型的团队，希望用目标牵引而不是用任务管控。
- 创业公司或新业务线，需要快速试错并公开对齐方向。
- 个人成长规划，用一页纸说清一个季度的重点。
- 转型期的组织，需要用公开目标打破部门墙、统一方向。
- 新员工快速理解团队当前重心，公开的 OKR 是最好的入口。

## 常见误区

- 把任务当 KR。"完成三次用户访谈"是任务，"用户流失原因被验证并形成可执行结论"才是结果。
- KR 不可衡量，写成"提升用户体验""优化架构"这类无法验收的表述。
- 数量太多，一个季度设了七八个目标，等于没有重点。
- 把 OKR 直接当考核指标，导致目标定得保守、数据被修饰。
- 只设 OKR 不做周检查，到季度末才发现偏离，已经来不及调整。
- 自上而下强压，员工没有参与感，OKR 变成另一种派活工具。
- 目标与 KR 脱节，KR 完成了但目标并没有推进。
- 每年换一套模板，不沉淀经验，团队反复从头摸索。
- 把 OKR 当成 KPI 的别名，两个词混用，团队分不清两者区别。

## 相关工具

- KPI：OKR 管突破方向，KPI 管业务健康度，两者是进攻与防守的分工。
- MBO（目标管理）：OKR 的源头之一，德鲁克提出的目标管理与自我控制是 OKR 的思想基础。
- SMART 原则：用来检查每个 KR 是否具体、可衡量、有时限。
- 平衡计分卡：当需要从财务、客户、流程、成长多个维度平衡指标时，可以借鉴它的框架。
- GROW 模型：在 OKR 复盘对话中，可以用 GROW 引导当事人自己找到改进方案。
- PDCA 循环：OKR 的周检查和季度复盘，本质上就是 PDCA 的循环。
- 艾森豪威尔矩阵：日常排优先级时，以 OKR 作为判断"重要"与否的依据。
