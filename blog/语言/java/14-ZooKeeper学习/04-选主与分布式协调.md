# 选主与分布式协调

## 1. 这是什么

很多人一听到 ZooKeeper，就会立刻联想到几个高频词：

- 选主
- 分布式锁
- 注册中心
- 协调服务

但如果继续追问：

- 为什么 ZooKeeper 能做选主？
- “协调”到底协调的是什么？
- 选主和加锁看起来不是两个问题吗，为什么总放在一起讲？
- 为什么一旦会话出问题，选主和锁逻辑就容易跟着失效？

很多人就会开始模糊。

这篇的目标，就是把这些问题串起来讲清楚。

如果先只记一句话，可以这样记：

> **ZooKeeper 擅长的不是帮你“做业务决策”，而是帮多个节点就“谁先执行、谁当前有效、谁已经下线”这类协调状态达成一致。**

所以无论是：

- 选主
- 分布式锁
- 成员管理
- 任务协调

本质上都属于同一类问题：

- **多个节点如何围绕共享状态有序行动，而不是各做各的。**

---

## 2. 为什么重要

只要系统从单机走向多机，协调问题就一定会出现。

比如你会遇到：

- 多个实例里，到底谁来当主节点？
- 某个定时任务，只能有一台机器执行，怎么保证？
- 一批消费者里，谁先处理某项共享资源？
- 某个节点挂了以后，其他节点怎么知道该接管？

如果这些问题处理不好，就会出现很多典型事故：

- 同一个任务被重复执行
- 主节点和备节点同时认为自己是主
- 锁看似拿到了，实际上多个客户端同时进入临界区
- 节点已经挂掉，但系统仍然把它当作活节点使用

所以这一章真正要回答的是：

> **分布式系统里“有序协作”这件事，为什么离不开 ZooKeeper 的节点、会话、顺序和通知机制。**

---

## 3. 先建立整体直觉：什么叫分布式协调

“协调”这个词很容易说得很空。

你可以先把它理解成一句更具体的话：

- **让多台机器在共享资源和共享状态面前，不至于互相打架。**

### 3.1 单机世界里怎么解决

在单机程序里，类似问题通常这样解决：

- 用 `synchronized`
- 用 `Lock`
- 用共享内存变量
- 用条件队列

因为：

- 线程都在同一台机器上
- 大家能看到同一块内存
- 进程内同步原语足够解决问题

### 3.2 分布式世界里为什么不一样

到了分布式系统里：

- 节点不共享内存
- 网络可能抖动
- 机器可能瞬间宕机
- 各节点看到的信息未必同时更新

所以很多单机里看起来很自然的动作，到了分布式环境就会变难：

- “我先抢到资源”
- “我现在是主节点”
- “前一个执行者已经退出”
- “所有人都知道配置已经变了”

因此协调组件存在的价值就是：

> **把这些“谁先、谁后、谁有效、谁失效”的判断交给一个大家共同信任的状态基座。**

ZooKeeper 就是这种基座之一。

---

## 4. 选主到底在解决什么问题

选主（Leader Election）最直白的目标是：

- **在多个候选节点中，选出一个当前负责主角色的节点。**

但真正难点不在“挑一个出来”，而在：

- 大家是否都承认同一个主节点
- 原主节点失效后能否及时重新选出新主
- 新旧主之间会不会短时间同时存在
- 其他节点如何感知主节点变化

### 4.1 哪些场景需要选主

常见场景包括：

- 主备服务切换
- 分布式任务调度中心
- 集群中的协调者角色选举
- 需要单点决策者的系统

比如：

- 只有主节点负责定时扫描订单超时
- 只有主节点负责生成某类全局控制命令
- 只有主节点负责向下游广播集群状态

### 4.2 为什么不能大家都做

有些任务天然只能有一个执行者。

例如：

- 同一批订单的补偿任务
- 同一份配置的最终发布动作
- 同一个分片的主协调调度

如果所有节点都同时做，就可能导致：

- 重复执行
- 写冲突
- 外部副作用翻倍
- 系统状态越来越混乱

所以选主的本质不是为了“体现谁更厉害”，
而是为了：

- **把某类全局职责在同一时刻收敛到一个节点上。**

---

## 5. 为什么 ZooKeeper 适合做选主

ZooKeeper 能做选主，不是因为它有一个叫“选主 API”的神奇接口，
而是因为它刚好具备选主最需要的几种能力：

- 临时节点
- 顺序节点
- 会话机制
- Watcher 通知
- 一致性的写顺序保证

下面逐个看。

### 5.1 临时节点：主节点失联后能自动撤销资格

如果一个候选者当选后，用普通持久节点表示“我是主”，
那它挂掉以后，这个标记可能还留在那里。

这就很危险，因为系统会误以为：

- 主节点还活着

而临时节点的好处是：

- 节点和会话绑定
- 会话过期后节点自动删除

于是：

- 主节点挂了或长期失联
- 它对应的临时节点消失
- 其他候选者就能感知并重新竞争

### 5.2 顺序节点：让“先来后到”变得可判定

如果多个候选者同时竞争，
系统必须有一种办法判断：

- 到底谁排在最前面

临时顺序节点就很适合做这件事。

例如多个客户端都在：

```text
/election/candidate-
```

下面创建临时顺序节点，
最终可能得到：

```text
/election/candidate-0000000001
/election/candidate-0000000002
/election/candidate-0000000003
```

这时序号最小的节点就可以认为自己当选。

### 5.3 会话机制：保证“在线资格”和“主身份”绑定

分布式协调里最危险的一类错误就是：

- 节点自己以为还活着
- 但系统其他部分已经看不到它了

ZooKeeper 的会话机制能帮你把：

- 节点在线资格
- 选主资格

绑定在一起。

也就是说：

- 只要会话有效，选主节点资格还成立
- 一旦会话过期，资格自动失效

### 5.4 Watcher：让其他节点及时知道主节点变化

选主不是只选出来就完了，
其他节点还得知道：

- 当前主是谁
- 主是不是已经失效
- 是否需要重新判断自己的状态

Watcher 的价值就在这里：

- 当关键节点删除或子节点列表变化时
- 候选者或观察者可以收到通知
- 然后重新检查当前主状态

所以：

> **临时节点负责“失效自动退出”，顺序节点负责“竞争有序”，Watcher 负责“变化可感知”。**

这三者组合起来，就很适合实现选主。

## 6. 一个经典选主流程怎么走

下面用最常见的“临时顺序节点选主”来建立直觉。

假设有 3 个候选节点：

- Node A
- Node B
- Node C

它们都想竞争主节点。

### 6.1 第一步：大家都创建临时顺序节点

在目录：

```text
/election
```

下面创建：

```text
/election/candidate-0000000001   -> Node A
/election/candidate-0000000002   -> Node B
/election/candidate-0000000003   -> Node C
```

### 6.2 第二步：比较序号

所有候选者读取 `/election` 子节点列表，
然后比较：

- 谁的序号最小

此时：

- Node A 对应最小序号
- 所以 Node A 成为 Leader

### 6.3 第三步：其他节点监听前驱节点

这里有一个很关键的优化思想：

- 不是所有节点都盯着最小节点疯狂监听
- 而是每个节点只监听自己前一个节点

例如：

- Node B 监听 `candidate-0000000001`
- Node C 监听 `candidate-0000000002`

这样做的好处是：

- 避免大量节点同时监听同一个目标
- 减少惊群效应

### 6.4 第四步：Leader 失效后触发重新判断

如果 Node A 挂了，会话过期，
`candidate-0000000001` 被删除。

这时：

- Node B 监听到了前驱节点删除
- 它重新检查自己是否已经成为最小节点
- 如果是，它就当选新 Leader

这就形成了一个自动接力的过程。

## 7. 为什么监听前驱节点，而不是监听整个目录

这是实战里特别重要的一个点。

很多初学者第一反应是：

- 所有人都监听 `/election` 目录变化，不就好了？

能做，但通常不优雅。

### 7.1 监听整个目录的问题

如果 1000 个客户端都监听整个目录，
当某个节点变化时，可能出现：

- 大量客户端一起被唤醒
- 大量客户端同时重新拉取子节点列表
- ZooKeeper 瞬间承受放大的读取压力

这就是典型的：

- **惊群效应**

### 7.2 监听前驱节点的好处

每个候选者只关心一个事实：

- 排在我前面的那个还在不在

只要它还在，我就不可能当选；
只要它消失，我才有必要重新判断。

所以监听前驱节点是一种更节制、更高效的协调方式。

你可以把这个思路记成一句口诀：

> **不是所有变化都值得所有人知道，只要让“下一个可能接班的人”先知道就够了。**

## 8. 分布式锁和选主为什么总放在一起讲

因为它们底层依赖的机制非常相似。

### 8.1 相同点

它们都在解决：

- 多个节点竞争同一份共享资格

而且通常都依赖：

- 临时顺序节点
- 序号比较
- 前驱监听
- 会话失效自动释放资格

### 8.2 不同点

但它们语义上还是有差别。

#### 选主更像：

- 在多个候选节点里选一个“当前负责人”

#### 分布式锁更像：

- 在多个竞争者里决定“谁现在可以进入临界区”

你可以粗略这样类比：

- 选主：选班长
- 分布式锁：决定谁先用会议室

所以它们底层套路常常相似，
但上层业务含义不完全一样。

---

## 9. 分布式锁的基本思路是什么

虽然这一篇重点是选主与协调，
但理解锁能帮助你把协调问题看得更完整。

一个经典锁流程通常是：

1. 竞争者在锁目录下创建临时顺序节点
2. 序号最小者获得锁
3. 其余竞争者监听自己的前驱节点
4. 当前持有者执行完任务后删除节点
5. 下一个竞争者感知变化后接力

例如目录：

```text
/locks/order-create
```

下面出现：

```text
/locks/order-create/lock-0001
/locks/order-create/lock-0002
/locks/order-create/lock-0003
```

此时：

- `lock-0001` 持有锁
- `lock-0002` 监听 `lock-0001`
- `lock-0003` 监听 `lock-0002`

### 9.1 为什么这比“建一个固定锁节点”更稳

有些人会想到一个更简单的做法：

- 谁先创建 `/locks/order-create` 谁就拿到锁

这种思路能作为最粗糙的入门理解，
但会有一些问题：

- 缺少公平性
- 重试逻辑容易混乱
- 大量竞争时容易惊群
- 对排队顺序表达不清

而临时顺序节点天然更适合表达：

- 谁先排队
- 谁在等待谁
- 谁该接力获得资格

## 10. 协调不仅仅是锁和选主

很多人一学 ZooKeeper，容易把“协调”缩成两件事：

- 锁
- 选主

其实协调还有很多常见形态。

### 10.1 成员管理

例如：

- 当前集群有哪些节点在线
- 哪些消费者还活着
- 哪些工作节点已经退出

这通常依赖：

- 临时节点表示在线状态
- Watcher 感知成员变化

### 10.2 配置通知

例如：

- 某个配置节点值变了
- 客户端收到通知后重新加载配置

这本质也是协调：

- 大家围绕同一个配置状态协同行动

### 10.3 任务分配

例如：

- 多个 worker 之间协调谁执行某份任务
- 避免重复消费或重复调度

### 10.4 主备切换

例如：

- 主节点异常后
- 备节点要及时接任
- 其余从节点要感知主节点已变化

你会发现，这些场景都离不开同一组基础能力：

- 节点存在性
- 顺序关系
- 在线资格
- 变化通知

这就是为什么 ZooKeeper 被称为“协调组件”。

## 11. 选主方案真正难的地方不只是“选出来”

初学者很容易把注意力放在：

- 怎样选出一个 Leader

但真正复杂的其实是后面这些问题：

- Leader 失效后多快能恢复
- 会不会短时间出现双主
- 重新选主后其他节点能否及时感知
- 新主接管时是否需要做状态恢复

### 11.1 为什么会担心双主

因为在分布式系统里，
“节点自己觉得自己没问题”和“系统其他部分认为它仍有效”不一定完全同步。

例如网络分区时，
可能出现一种危险状态：

- 旧主还在本地运行
- 但它和 ZooKeeper 的会话已经过期
- 其他候选者重新选出了新主

如果旧主没有正确感知并主动停掉自己的主逻辑，
就可能发生：

- 新旧两个节点都在执行主职责

这就是双主风险。

### 11.2 所以选主方案一定要带业务侧保护

不能只依赖“ZooKeeper 帮我选出来了”，
还要结合业务实现：

- 主节点周期性确认自己资格是否仍有效
- 一旦会话异常或节点被删除，主动停止主逻辑
- 外部副作用操作要有幂等和防重保护

这点非常重要。

---

## 12. 会话失效为什么会直接影响协调逻辑

ZooKeeper 的很多协调能力，本质上都是“会话驱动”的。

只要你用了：

- 临时节点
- 依赖节点存在性判断资格

那就等于把协调状态和会话绑在了一起。

所以一旦发生：

- 网络抖动
- 长时间 GC 停顿
- 客户端阻塞
- 服务端压力过大

导致会话过期，可能马上触发：

- 主节点资格丢失
- 锁自动释放
- 服务实例被认为下线
- 集群成员列表变化

这也是为什么：

> **ZooKeeper 的会话问题，看起来像基础设施问题，实际上会直接放大成业务协调问题。**

## 13. 一个主备切换的小例子

假设有两台调度服务：

- Scheduler A
- Scheduler B

它们都竞争 `/scheduler/election` 下的主资格。

### 正常情况

- A 创建的临时顺序节点序号最小
- A 成为主调度器
- B 监听自己的前驱节点

### A 异常

- A 机器宕机或会话过期
- A 的临时节点被删除
- B 收到监听通知
- B 重新比较后成为主调度器

### 切换后的关键点

B 当选新主，不代表事情已经完全结束。

它通常还需要做：

- 重新加载任务状态
- 接管未完成任务
- 确认旧主遗留动作是否需要补偿
- 对外宣告自己成为新的主节点

所以你要意识到：

- **ZooKeeper 负责的是“协调资格切换”**
- **业务系统还要负责“主职责安全接管”**

这两层不能混为一谈。

## 14. 常见误区

### 14.1 误区一：选主就是随便挑一个节点出来

不对。

真正难的是：

- 所有人都承认同一个主
- 主失效时能及时重选
- 不出现长时间双主

### 14.2 误区二：只要用了临时节点，就绝对不会有双主

也不对。

临时节点能很好地表达“资格失效”，
但业务侧如果没有及时感知并停止旧主逻辑，
依然可能短时间出现双主风险。

### 14.3 误区三：所有竞争者都监听根目录最简单

简单不等于合适。

大量竞争场景下这么做容易造成：

- 惊群
- 无效唤醒
- ZooKeeper 压力升高

### 14.4 误区四：ZooKeeper 负责整个协调流程的全部语义

不是。

ZooKeeper 提供的是：

- 节点模型
- 顺序能力
- 会话绑定
- 变化通知

而真正的业务补偿、幂等、防重、状态接管，
还需要你自己设计。

---

## 15. 学这一章最该抓住的 5 个点

1. **分布式协调的核心是让多节点围绕共享状态有序协作**
2. **选主本质是把某类全局职责在同一时刻收敛到一个节点**
3. **临时顺序节点是 ZooKeeper 实现选主和锁的经典基础组合**
4. **监听前驱节点是减少惊群、实现有序接力的关键技巧**
5. **ZooKeeper 解决的是资格协调，业务系统还要解决接管、幂等和补偿问题**

只要这 5 个点吃透，
你对选主和协调的理解就不会只停留在“会背流程图”了。

## 16. 奇淫技巧

### 16.1 面试或写方案时，优先讲“资格”而不是讲“锁”

很多协调问题表面上像锁，
但更通用、更本质的表达其实是：

- 谁当前拥有资格
- 资格何时失效
- 其他人如何接力

用“资格模型”去理解，选主、锁、成员管理会一下子统一起来。

### 16.2 排查协调问题时，先沿着这条链路找

先问 4 个问题：

1. 当前资格是靠什么节点表达的？
2. 这个节点是持久节点还是临时节点？
3. 资格变化后是谁在监听？
4. 监听触发后业务逻辑有没有真的完成接管或退出？

很多问题都能沿这条链迅速定位。

### 16.3 设计选主方案时，一定补上“失去资格后的自杀式降级”

也就是：

- 旧主一旦发现自己会话异常
- 或发现资格节点不再属于自己
- 就要立即停止主逻辑、停止对外写入、停止调度

这比“只负责抢主，不负责退主”安全得多。

## 19. 自测核对要点

- 选主的目标是让全局职责在同一时刻只有一个有效执行者
- ZooKeeper 通过临时顺序节点、会话和 Watcher 很适合表达资格竞争与接力
- 前驱监听能显著减少惊群和无效竞争
- 协调系统里真正危险的不是“没选出主”，而是“多个人同时以为自己是主”
- 业务系统必须补上退主、幂等、补偿和接管逻辑，才能把协调方案做稳
